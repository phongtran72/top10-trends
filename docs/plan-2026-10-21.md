# Plan: the embedding fix and the rebuild

Written on Wednesday 21 October 2026, 7:00 am New York time (11:00 UTC), for the owner to read and approve. Times are New York time (EDT), with UTC in parentheses where a time names a run.

## In short

- **The problem:** the 8-bit model makes different vectors on different GitHub machines, so a close match can depend on where an hour runs, and a rebuild can't reproduce the live topics.
- **The fix:** the full-precision (fp32) model of the same name. It made identical vectors on every machine tried, and at the same threshold, 0.86, it matches the way the site matches today.
- **One change, one restart:** the switch, two small fixes that make a rebuild exact, the retrained category model, and the rebuild of all history, together on **Friday 23 October**.
- **The window:** it is enough, with three spare days before the oldest stored lists are deleted on 28 October.

## 1. Why the vectors differ

The predictions session compared 617 live topics that have a single item (their centroid is that item's vector) with the same text embedded on the owner's PC. Only 27% were identical; the rest were off by cosine 0.97 to 0.99, and 0.90 at worst.

**What the processor log shows** (task 4.8, merged 18 October). Every hourly run since 9:07 am on 18 October (13:07 UTC) logs its CPU and a fixed text's vector. Over 72 runs, to 6:07 am today (10:07 UTC), there were two vectors, never more:

| Probe | Runs | Machines |
| --- | --- | --- |
| A, the same as the owner's PC | 30 | AMD EPYC 9V45 (14), AMD EPYC 9V74 (9), Intel Xeon Platinum 8573C (5), Intel Xeon 6973P-C (2) |
| B, different | 42 | AMD EPYC 7763 (39), AMD EPYC 9V74 (3) |

**Lined up with the vectors** (the predictions session, 630 one-item topics, up to ten per hour):

- **B hours (40):** not one vector of 376 identical. They are off by 0.02 to 0.07, enough to move joins near 0.86.
- **A hours (29):** 63% identical, and the rest off by less than 0.01.

The per-run table is in the predictions session's note `research/findings/embedding-by-machine.md` (on its branch, coming to main with its next pull request).

So there are two 8-bit paths: machines with the VNNI instructions, and the AMD EPYC 7763 (and some 9V74 machines) without them. More than half of all hours run on the second. GitHub's free runners can't be pinned to one kind.

## 2. The full-precision model

**Same vectors everywhere.** Seven dry runs of the hourly workflow from the test branch (10:40 to 10:48 UTC today; dry runs write nothing) all printed the same probe as the owner's PC. They ran on an AMD EPYC 7763, four AMD EPYC 9V74, an AMD EPYC 9V45 and an Intel Xeon Platinum 8370C. After the switch the predictions session repeats its comparison on live hours, the wider test.

**Run time.**

- **Today's 8-bit runs:** the pipeline takes 17 to 30 s, and a whole job about a minute.
- **The fp32 dry runs:** the pipeline took 6 to 12 s, without the database, and a whole job 45 to 57 s.
- **On the owner's PC:** fp32 is about 2.8 times slower (200 texts in 21 s, against 7.5 s).
- **Verdict:** a live run should stay near a minute, far inside the 5-minute budget.

**The model cache.** The file is 547 MB, against 137 MB. The workflow's cache key changes to `…-fp32`. The first run on main downloads it from Hugging Face (about 10 s on GitHub's network) and every later run restores it.

- **At 0.86** the totals agree within 1%. Individual joins shuffle: 171 cross-platform pairs are made only by the 8-bit model and 212 only by fp32.
- **The joins that differ.** I read 40 of each. Both sides were about two thirds right and one in six wrong:
  - only 8-bit: "f1 standings" with Verstappen's win, "bubonic plague" with Russia's plague leak, and "Djokovic" with "qinwen zheng" (wrong);
  - only fp32: "OpenAI engineer arrested" with the recording-device inquiry, "iPhone Duo" with its backorders, and "#October7" with an October calendar (wrong).
- **At 0.88 and above:** fewer mixed topics, but 13% fewer stories matched across platforms. That is the trade the review of 12 October already turned down.
- **The two hours with a name twice:** I haven't traced them yet. I'll check them in the rehearsal (step 4).

## 4. What ships, in one pull request

1. **The fp32 model**, at 0.86.
2. **Whole-hour ages.** Today a topic stops taking members once it is 48 hours old, counted to the second. In the run exactly two days on, a few seconds of start time decide it, and a replay can decide differently. The rule becomes: the run's clock hour against the topic's first clock hour.
3. **The stored text in live runs.** A live run embeds an item's extra text as collected; storage trims it and keeps at most five texts of 1,000 characters. Live runs will embed the stored form, so a replay reads exactly what the live run read. This is rare in practice, and needed for an exact rebuild.
4. **The retrained category model (c2).** The predictions session retrained it on fp32 vectors: it answers 67% of trends with a text and is right on 96%, as the current one does. The current model refuses fp32 vectors, so the two ship together; without c2 the category step would switch itself off.
5. **The rebuild tool**, changed so that no hour is missed:
   - build the whole history in memory on the owner's PC from the stored lists;
   - then swap it into the database in one transaction, between two hourly runs.
   - Rebuilt hours use each live run's own start time, so their topics' times match the live ones.

Items 1 to 3 change rankings: this is ranking version **`r8`**. The version label becomes `nomic-embed-text-v1.5.fp32.384/t0.86/r8`, and rebuilt rows carry `…/r8+replay`. The model part changes from `q8` to `fp32`, so this is a new family by itself, and no extra generation tag is needed.

## 5. Together, not one after the other

**I recommend the switch and the rebuild together, at one moment.**

- **One restart.** The forecasts' history restarts once, not twice.
- **No tag needed.** No live `r8` hour exists before the rebuild, so no topic id is ever reused within a family. The family change alone keeps Trend Forecaster's stored topic ids from matching rebuilt topics.
- **The risk is small.** The dry runs have already tried fp32 on GitHub's machines.
- **The cutover is guarded:**
  - the in-memory build is rehearsed first;
  - the swap is one transaction, so a failure leaves the old rows in place;
  - a bad merge can be reverted.

One after the other would let us watch a day of live `r8` first. But then the live `r8` hours and the rebuilt ones would share a family, so the rebuild would need a generation tag (`…/t0.86.g2/r8`), and the forecasts would restart twice.
