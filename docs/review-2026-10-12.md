## 2. The hour that was never started

**What happened.** At 11:07 am on 7 October (15:07 UTC) the Cloudflare Worker asks GitHub to start the run, as it does every hour. GitHub's status page records an outage that it opened seven minutes later, at 11:14 am (15:14 UTC): "Incident with Git Operations, Pull Requests and Actions", degraded availability, closed at 12:25 pm (16:25 UTC). The two missed hours on 5 October fall inside another outage, "Incident with Actions", 3:11 pm to 6:49 pm (19:11 to 22:49 UTC).

**What the code does.** `worker/src/index.ts` sends one request. If GitHub answers with an error it logs the status and throws. Nothing tries again, and Cloudflare does not re-run a failed cron.

**What Cloudflare still has.** Not checked. Neither Cloudflare's command-line tool nor the browser on this machine is signed in, and I don't enter passwords. The Worker's log for that minute would show the exact status GitHub returned; Cloudflare keeps those logs only for a few days, so it is probably gone. The owner can look in the Cloudflare dashboard under Workers, `top10-trends-cron`, Observability.

**The smallest thing that would have helped.** A second and third cron in the same Worker, at :22 and :37, that first ask GitHub whether a `collect` run was created this hour and has succeeded or is still running, and start one only if not.

- It covers both failures seen so far: a request GitHub refused (7 October) and a run GitHub created but never ran (5 October). A retry inside the first request covers only the first kind.
- It is about 25 lines in the Worker and two more cron lines. Cloudflare's free plan allows five.
- It costs nothing in a normal hour: one read request to GitHub, no extra run, no extra X request.
- A run that starts at :22 or :37 still lands in its hour.

It is not a guarantee. On 7 October the outage lasted until 12:25 pm, so the 11:22 and 11:37 tries would have met the same outage; the 12:07 pm run did get through while it was still open. Two more tries would have given each of the three hours a real chance, and nothing more can be said than that.

The cost of a missed hour is not on this site, which just shows the previous list for an hour longer. It is in Trend Forecaster, where three missed hours voided 194 questions.

"Joined by meaning" leaves out topics that are one name on every platform, which every threshold gets right. A "big mixed topic" shows six or more different names across its platforms, the mark of a catch-all.

- **Lower is clearly worse.** At 0.82 there are 40% fewer topics in all because stories fuse, and wrong merges return: "Texas A&M" with "texas longhorns", October nail art with "October 7".
- **Higher drops right merges faster than wrong ones.** From 0.86 to 0.88, 111 topics lose a cross-platform pair. I read 75 of them: 47 right, 14 wrong, 14 loose or unclear.
  - Lost at 0.88: "Walt Jr" with the Reddit post on the actor's death; Bluesky's "Eagles trade Cam Jurgens to Ravens" with Google's "cam jurgens"; "Markwayne Mullin's New York City press conference" with "markwayne mullin".
  - Still made at 0.88: "Cat 3" with "#Cats"; "Deno" with "DeNA".
- **So the band between 0.86 and 0.88 is where the errors gather** (63% right there, against 88% overall), but it is still mostly right merges, and of the kind the combined list exists for: a Bluesky sentence with a Google query.
- **No threshold** produced a top 10 with the same name twice.

Two limits. The replay is close to the live site, not equal to it: the predictions session measured 93% of topics identical per hour. And it begins on 2 October, so it has none of the topics made before then.

### The larger problem: topics that never end

A topic takes new members as long as something joined it in the last 48 hours. A subject that trends every day (baseball, tennis, Ukraine) never goes 48 hours without a match, so its topic never ends. Its centre is the average of everything that ever joined, so it drifts from one story to a whole subject. Its label stays what it was on the first day.

**How much of the top 10 it touches.** Of 1,900 Global top-10 places since `r6` began (190 hours):

| Topics I judged | Top-10 places | Hours | Of them in the top 3 |
| --- | --- | --- | --- |
| Wrong (cross-platform) | 80 | 73 | 40 |
| Catch-all on one platform, such as "efl championship" | 70 | 63 | 27 |
| **Wrong or catch-all** | **150 (8%)** | **109 of 190** | **67** |
| Loose (teammates, a sport in general) | 64 | 54 | 35 |

This is a floor: I judged every cross-platform topic, but only the ten largest single-platform ones.

**The examples.**

- **"MLB wild card series begins"** was created on 30 September. The wild card round ended long ago; the topic has since been in the top 10 for 32 hours, as high as #1, holding 18 different baseball names.
- **"Banega Swasth India"** was an Indian health campaign on 2 October. It then took in "Índia", "Brazil", "INDONESIA JUARA", "russia", "Putin" and "Ukraine", and spent 21 hours in the top 10, as high as #1, over Ukraine news.
- Others of the same kind: "May October" (27 names on 6 platforms), "america vs cruz azul" (every Latin American match), "karen khachanov" (tennis), "efl championship" (English football), "weather today".

**A looser sign, for scale.** One top-10 place in five goes to a topic more than two days old, and in 72% of those the label is none of the names its current members have. A stale label is not always a wrong topic ("pneumonic plague" ran four days under one label and is one story), so this overstates the damage; the table above is the fair count.

This is also what failed Gate 2 on 10 October, and it will make Claude's names go stale the same way, since a topic is named once.

### Candidate fixes, measured

Two small changes to matching were replayed over the same 246 hours, each a replay-only option on the branch `review-experiments`; neither is live.

- **A fixed centre.** A topic's centre stays its first item's vector, so later members can't pull it toward a whole subject.
- **An age limit.** A topic takes no new member once it is 48 (or 24) hours old; whatever arrives next starts a fresh topic with a fresh label.

| Variant | Topics | Top-10 places from topics over 48 h old | Topics with 10+ names | Top-10 places on 2+ platforms | Cross-platform pairs kept, of 1,085 |
| --- | --- | --- | --- | --- | --- |
| As live | 4,711 | 398 | 27 | 483 | 1,085 |
| **Age limit 48 h** | 5,105 | 13 | 12 | 471 | 802 |
| Age limit 24 h | 5,682 | 0 | 5 | 463 | 620 |
| Fixed centre | 5,105 | 252 | 4 | 408 | 548 |
| Fixed centre + 48 h | 5,328 | 9 | 1 | 398 | 514 |
| Fixed centre at 0.84 | 4,752 | 267 | 10 | 465 | 670 |

No variant produced a top 10 with a name twice.

**What each one costs.**

- **Age limit 48 h** removes the old catch-alls (398 old places down to 13) and keeps 97% of the multi-platform places. The pairs it drops are almost all inside the long-running catch-alls: 47 in a Ukraine topic, 30 in the baseball one, 24 in a diesel one, 17 in a Latin American football one. A real story that runs past two days ("pneumonic plague") starts a second topic and a second page on its third day.
- **Age limit 24 h** is cleaner still, but nothing is then old enough for the home page's "change since yesterday", and it makes 21% more topics.
- **A fixed centre** ends the mixed topics that form within a day, which no age limit touches, but it drops half of the cross-platform pairs, right ones included. As tested it costs too much.

**Recommendation: the 48-hour age limit, as ranking version `r7`.** It is the smallest change and it removes the worst cases, the "Banega Swasth India" kind.

**What it does not fix.** Catch-alls that form inside two days (12 of the 27 big topics remain; "efl championship" was 23 hours old when it failed Gate 2), short-name confusions ("Iowa" with "Nebraska"), and missed merges between a bare name and a sentence ("Columbus"). So Gate 2 would improve but might still not pass. The fixed centre shows the same-day catch-alls can be ended; a finer version of it is the next thing to test, not something to ship now.

## 5. Should history be rebuilt?

**Recommendation: not under today's rules.** Fix the catch-all problem first, then rebuild once under the fixed rules, finishing by about 25 October.

**Why a rebuild is on the table.** Each ranking change restarted the forecast models' training history, which now begins on 5 October. A rebuild replays every stored hour under one set of rules, so the history would be one piece again.

**What a rebuilt hour cannot reproduce.**

| Missing before | What the rebuilt hours lack |
| --- | --- |
| 2 October, 2:07 pm (18:07 UTC) | Google's headlines and Bluesky's descriptions, so matching runs on titles alone and the news count is zero |
| 1 October, 11:07 am (15:07 UTC) | Bluesky's status, so stale Bluesky trends are kept |
| 4 October, 2:07 am (06:07 UTC) | The UK, Canada and Australia feeds, so the Global view is the US view |
| 1 October, 8:07 am (12:07 UTC) | Reddit |

So the hours a rebuild can make properly comparable with live ones start on the afternoon of 2 October. That adds about 57 hours to a history that already holds 188, and for the Global view only the hours from 4 October.

**What it does to links.** A rebuild deletes every topic and makes them again, so every topic gets a new id, and a topic's address changes whenever its first hour or its first name comes out differently. Expect most `/t/...` links shared so far to break, the sitemap's topic pages to change, and the archive to be rewritten for every hour, including the hours since launch. Trend Forecaster's stored topic ids would stop matching; it also matches by title, which survives.

**How long it takes.** About an hour, which is the difficulty. The only real measurement is the rebuild of 1 October: 3 minutes for 28 hours, when an hour held half as many items. For 313 hours at today's size that scales to 50 to 70 minutes, longer than the gap between two hourly runs. So the hourly trigger would have to be paused for one run (one more missed hour, announced), or the rebuild taught to stop and resume around the run.

**The deadline.** Stored lists are deleted after 28 days. The lists of 30 September go on 28 October, and one more day goes each day after. The hours worth rebuilding (from 2 October) start to go on 30 October.

**Why wait for the fix.** A rebuild under `r6` would write the catch-all topics of section 4 into the whole history and then need redoing after the fix. The age limit also makes about 8% more topics. One rebuild after the fix gives the training table and the archive the same clean rules from 2 October on.

**The predictions session's view** (its note is on PR #31):

- A rebuild is worth little to the forecasts and wouldn't hurt them: 57 trainable hours added to 188 live ones, in a history that grows by 24 a day.
- It would train on the rebuilt hours from 2 October, 2:07 pm (18:07 UTC), US view only, and never score on them.
- A rebuilt hour is close to the live one, not equal. It replayed 83 recent hours and compared them with production: 93% of topics identical in the US view; the same top 10 in 44 hours, 9 of 10 in 29, 8 or fewer in 10.
- A reset of topic ids costs its files nothing.

**Trend Forecaster's one requirement.** Its stored marks are a topic id plus the version family (model and threshold). A rebuild under the same family reuses the ids for different topics, and its old questions would then match the wrong topic without any error. So a rebuild must do both of these:

- carry a generation tag in the version label before the `/rN` part (for example `…/t0.86.g2/r7`), so old marks can't match new ids. The research loaders group by that same family, so they would start a new one at the rebuild, which is what a rebuild is;
- be announced with its start time in UTC before it runs, as PLAN.md already requires.

**Putting it together.** A rebuild by itself buys 57 hours. A rebuild together with the catch-all fix buys much more: without it, the fix would restart the history yet again on the day it ships; with it, the history is one piece from 2 October. That is the reason to do the two together and not to rebuild now.

**The pace.** About 460 new topics a day (2.5 KB each, most of it the 384-number centroid) and about 5,600 snapshot rows a day (235 bytes each). The permanent tables grow by about 77 MB a month, more than the 60 to 65 MB PLAN.md estimated. The 28-day tables level off at about 90 MB at the end of October.

**Months left.** About 5: the 500 MB limit would be reached in early March 2027.

**Recommendation: nothing this month, the first option before the end of the year.**

- **Drop the centroid of topics not seen for 48 hours.** Matching never reads them again. It cuts the topics table's growth from about 35 MB a month to about 5, and takes the runway to about 8 months. The predictions session should say first whether it uses old centroids.
- Keeping snapshots only for scored topics saves little: about 9 rows in 10 are scored.
- Supabase Pro ($25 a month) is the fallback, and a subscription, which the owner prefers to avoid.

If the catch-all fix in section 4 shortens topic lifetimes, more topics are created and this pace rises, which is one more reason to drop old centroids at the same time.
